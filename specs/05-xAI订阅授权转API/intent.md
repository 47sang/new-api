## 问题

我买了 Grok 订阅（SuperGrok 或 X Premium+），但 new-api 里的 xAI 渠道（48 号）只接受按量付费的
API Key——订阅额度在网关侧完全用不上，想用 Grok 就必须再买一份 API 额度。而订阅这条路在手机端
已经跑通过：Mika 用 xAI 官方的设备码（OAuth 2.0 Device Code，RFC 8628）登录拿到访问令牌，
直接调 `https://api.x.ai/v1/responses`，不转协议、不过中转。网关侧缺的正是这同一能力：
把「一次 xAI 账号登录」变成网关里一个普通渠道，下游用标准 OpenAI 兼容接口调用，
用量走订阅而不是 API 额度。

需要说明的是，网关**读不到** Mika 里存的那份授权：Mika 把会话 JSON 用 Android Keystore 里的
AES/GCM 密钥加密存在手机本地，密钥不出硬件保护区、卸载即失效，也没有导出入口。所以网关必须
自己跑一次设备码登录——好在服务端比手机端更简单：不需要本机回调服务器，也不需要前台服务保活，
登录一次拿刷新令牌长期续。

## 预期成果

1. 新增一种「xAI 订阅」渠道：管理员在渠道编辑页点「登录 xAI 账号」→ 界面弹出设备码短码和验证
   网址 → 管理员在浏览器里完成确认 → 网关自动拿到令牌，存进渠道 key 字段（OAuth 会话 JSON，
   与现有 57 号 codex 订阅渠道同一模式），全程不用手填任何 Key。
2. 该渠道的请求打到 `https://api.x.ai/v1/responses`，请求头用订阅访问令牌；下游用标准的
   `/v1/chat/completions` 或 `/v1/responses` 调用，无感知差异。
3. 访问令牌快过期时自动用刷新令牌续期，续到的令牌写回渠道；刷新被终局拒绝（`invalid_grant`
   等）时渠道标记为登录失效，后续请求明确报错提示重新登录，而不是反复 401。
4. 网关计量计费照常工作：从上游响应的 usage 统计 token、照常扣额度；订阅侧自己的限额
   （429 限速、403 档位不够）由 xAI 执行，网关透出可读的错误原因。
5. 调用返回 403 时有明确提示「订阅档位不能用这个接口，请改用 xAI API Key」，不重试、不静默换路。
6. 退出登录只清网关本机的令牌，渠道和模型列表保留，重新登录即可恢复。

## 受影响的用户和系统

- **用户角色**：管理员（配置渠道、完成一次浏览器登录）；下游 API 调用方（无感知，仍走标准接口）。
- **涉及模块**：
  - `relay/channel/xai/`（订阅模式的令牌来源，API Key 模式行为不变）
  - `service/`（新增 xAI OAuth：设备码流程 + 令牌刷新 + 定时续期任务）
  - `controller/channel.go`（新增「开始登录 / 查询登录状态」接口）
  - `web/`（渠道编辑页登录按钮、设备码短码与验证网址展示、登录状态）
- **新增模块**：`service/xai_oauth.go`（设备码登录与刷新，参照 `service/codex_oauth.go`）、
  凭证定时刷新任务（参照 `service/codex_credential_refresh_task.go`）、新渠道类型常量。
- **参照先例**：57 号 `ChatGPT Subscription (Codex)` 渠道——「订阅授权存进渠道 key JSON +
  自动刷新 + 适配器取令牌」的完整模式，本次照搬而不另造轮子。

## 目标 / 非目标

**目标**

- 订阅授权变成网关里一个普通渠道，下游零改动调用 Grok 模型。
- 令牌全自动续期，管理员除非主动退出或被 xAI 撤销，否则不再需要碰登录流程。
- 计量、计费、日志、错误提示与现有渠道一致，不特殊对待。

**非目标**

- 不做多订阅账号轮换或负载均衡：一个订阅账号就是一个渠道，撞订阅速率上限是预期行为。
- 不做按下游用户的配额隔离（订阅限额由 xAI 侧执行，网关只透出）。
- 不把用量同步回 xAI 网页端，也不做 xAI 的图片 / 视频等其他端点，本期只做 responses 聊天。
- 不改现有 xAI（API Key）渠道的任何行为。

## 约束

- **客户端身份复用 xAI 官方命令行工具的公开 client_id**（与 Mika 同一個 ID）。这不是 xAI 给
  本项目注册的应用，xAI 可能限制这种用法、账号有被限制的风险；登录界面必须前置写明，
  不点「继续登录」就不发生。项目内 codex 渠道是同一模式，风险自负。
- **「买了订阅就能用」不保证**：门槛是授权 scope 里含 `grok-cli:access` 或 `api:access`，
  且调用不返回 403；有的档位登录成功也调不了，界面需提示改用 API Key。
- 安全边界照搬 Mika：OIDC 发现文档的 issuer 与各端点主机必须通过白名单校验
  （`auth.x.ai`），对不上就拒绝、请求不发往别的主机；验证页主机限定 `auth.x.ai` /
  `accounts.x.ai`，否则回落固定官方页。
- 访问令牌、刷新令牌不进日志、不进诊断信息、不出现在界面（用户码除外）。
- 与 Mika 不共享令牌：两边各自独立登录同一账号，互不影响。
- 单订阅账号扛整个网关流量会频繁撞 429，这是订阅模式的固有上限，不作为缺陷处理。

## 已确认决策（2026-11-04）

| 议题 | 结论 |
| --- | --- |
| 授权来源 | 网关自己跑设备码登录，不读取 Mika 的授权（Keystore 加密，技术上不可导出） |
| 授权流程 | OAuth 2.0 设备码（RFC 8628），服务端无需本机回调 |
| 调用路径 | 直连 `https://api.x.ai/v1/responses`，不转成别的协议 |
| 存储模式 | OAuth 会话 JSON 存进渠道 key 字段，照 codex 渠道先例 |
| 集成方式 | **方案 A**：在 fork 里加「xAI 订阅」渠道，深度集成、计量计费原生 |
| 渠道形态 | **新增独立渠道类型**（与 codex 一致；订阅与 API Key 两种计费分清，不给 48 号 xai 渠道加分支） |
| 登录入口 | 渠道类型天然支持多渠道，一期先做管理后台单账号登录，不额外做批量/多账号界面 |
| 下游计费 | **免费放行**：该渠道模型定价设 0，不扣下游配额；网关仍照常记录 token 用量 |
| 实施顺序 | 先后端（设备码登录 + 自动续期）跑通并确认订阅档位真能调用，再补前端与错误处理 |
| 合并冲突 | 已解决并单独提交；dev 分支预先存在的红灯测试（访问令牌作用域声明缺失）另行单独提交修复 |

## 待确认问题

- [x] 集成方式：方案 A / B / C？
方案 A（fork 加渠道）。理由：计量计费原生、与已有自定义提交一致；旁路方案要多一跳且用量统计依赖旁路如实回传。
- [x] 渠道形态：新增独立渠道类型，还是给现有 xai 渠道加分支？
新增独立类型。两种计费来源（订阅 vs API Key）在渠道列表、报错提示、失效处理上都不同，混在一个类型里要靠 key 格式猜，容易错。
- [x] 登录入口：单账号还是多渠道？
一期单账号。渠道类型本身支持建多个（每个 Grok 订阅一个渠道），本期不额外做批量管理界面。
- [x] 下游计费：定价 0 免费放行，还是照常计费？
免费放行（定价 0）。用量本身走 Grok 订阅，网关侧不向下游收费；用量日志照常记录，便于观察订阅消耗。
- [x] 实施顺序：先跑通再补前端，还是一起做？
先后端跑通。订阅档位能否调用 `/v1/responses` 是这个功能成立的前提，先用最小后端验证掉这个不确定性，再投入前端。
